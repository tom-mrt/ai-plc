> 🚨 **最重要原則: 「動くシステム」を生み出す**


  設計書やスキーマ定義だけでは「完了」にならない。


  実際にローカルDB、外部DB、コード、Markdown/YAML成果物などが存在して動作または利用可能であることが完了条件。

## Agent定義の標準構造

### Goal

「[System Name]を設計・実装し、実際に動作する状態にする」

### Input

- 要件定義（何を管理するか）
- スコープ（プロパティ数・ビュー数の目安）
- 既存システムとの接続点（Relation先等）
- 初期データ（あれば）

### Output

- **Database / 実装成果物**（スキーマ + ビュー/クエリ + 初期データ、または動作するシステム）
- 初期データ投入済み
- 使い方ガイド（付属ドキュメント）

### Execution Flow（エスカレーション型）

| Phase | タイプ | アクション | 出力 |
| --- | --- | --- | --- |
| 1. 設計 | Autonomous | DBスキーマ設計・プロパティ定義・ビュー設計 | 設計案 |
| 2. 設計承認 | Mob | プロパティ・ビュー・データ構造の確認 | 承認済み設計 |
| 3. DB/成果物作成 | Autonomous | 実際にSQLite DB、外部DB、コード、または成果物ファイルを作成 | Database / Artifact |
| 4. ビュー・クエリ追加 | Autonomous | 必要なビュー、クエリ、一覧、または利用導線を追加 | Views / Queries |
| 5. データ投入 | Autonomous | 初期データ・テンプレートを投入 | Data |
| 6. 検証 | Mob | 実際に動作確認・調整指示 | フィードバック |
| 7. ドキュメント | Autonomous | 使い方ガイド作成（DBの付属） | ガイドページ |

### Guardrails

- Phase 3で実際にDBまたは成果物ファイルを作成すること（設計書だけで止めない）
- Relation先や参照先が存在することを確認してから関連フィールドを設定
- ビュー、クエリ、一覧、操作手順のいずれかを最低1つ用意する
- テンプレートが必要な場合はMarkdown/YAML/DB初期データとして作成
